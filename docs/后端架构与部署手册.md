# 言喵后端：架构决策与腾讯云部署手册

> 面向执行，不是概念介绍。看完应当能独立把这套后端跑起来并上线。
>
> 版本：v1.0（对应 `server/` 目录与 `双端小程序混合云架构建议.html` 的长期多端架构）

> 当前第一阶段以微信小程序快速验证为目标，已新增微信·云开发接入骨架，见 `docs/微信云第一阶段接入说明.md`。本手册的自建服务端方案作为后续多端、复杂队列和生产 AI 任务的迁移目标保留。

---

## 一、结论

| 决策项 | 选择 | 理由 |
| --- | --- | --- |
| 托管形态 | 腾讯云轻量应用服务器（上海，2核2G） | 成本可控，完全控制权，非小程序用途也能复用 |
| 后端形态 | 自建标准 HTTP API（Fastify + PostgreSQL） | 微信 / 抖音 / H5 / App 都只是客户端，数据天然共享 |
| 媒体存储 | 腾讯云 COS 私有桶 + 签名 URL | 图片不经过 2G 小机器，省带宽也省磁盘 |
| AI 生成 | 火山方舟 Seedream，适配层隔离 | 与既定架构一致，换供应商不改业务代码 |
| 任务队列 | PostgreSQL 表 + `FOR UPDATE SKIP LOCKED` | 省掉 Redis 的 100MB+ 内存，2G 机器扛得住 |
| 鉴权 | JWT access + 数据库存储的 refresh | 多端无状态，可按设备精确吊销 |

### 为什么长期保留自建服务端方案

微信云开发适合第一阶段的微信小程序闭环，但它的原生数据链路主要围绕微信小程序和云函数。后续如果上抖音小程序、H5 或 App，所有请求都绕道云函数做代理，或需要增加独立服务层。

因此当前选择是：P0 用微信云快速验证上传、猫咪身份和作品生成闭环；多端共用数据、复杂 AI 队列和生产级运营能力成熟后，再迁移到本手册中的自建 API + COS + Worker。

```
│ 微信小程序    │  │ 抖音小程序    │  │ H5/App  │
└──────┬───────┘  └──────┬───────┘  └────┬────┘
       │  Bearer JWT      │               │
       └──────────┬───────┴───────────────┘
                  ▼
        ┌───────────────────────┐
        │  Nginx (443, HTTPS)   │
        │  反代 127.0.0.1:3000   │
        └───────────┬───────────┘
                    ▼
        ┌───────────────────────┐        ┌──────────────┐
        │  API 进程 (Fastify)    │───────▶│ PostgreSQL   │
        │  pm2: yanmiao-api     │        │ 本机 5432     │
        └───────────┬───────────┘        └──────────────┘
                    │ 写任务                  ▲
                    ▼                        │ 认领任务
        ┌───────────────────────┐             │
        │  generation_job 表     │─────────────┘
        └───────────┬───────────┘
                    │
        ┌───────────▼───────────┐        ┌──────────────┐
        │  Worker 进程           │───────▶│ 火山方舟      │
        │  pm2: yanmiao-worker  │◀───────│ Seedream 生图 │
        └───────────┬───────────┘        └──────────────┘
                    │ 转存结果
                    ▼
        ┌───────────────────────┐
        │  COS 私有桶 + CDN      │
        └───────────────────────┘
```

客户端上传图片时**直接 PUT 到 COS**，服务器只负责签名。这是 200GB/月流量套餐能撑住的关键——否则所有图片上下行都算在这台机器的流量里。

## 四、数据模型要点

| 表 | 作用 | 关键约束 |
| --- | --- | --- |
| `app_user` | 账号 | `phone` 唯一（未绑定时为 NULL） |
| `user_identity` | 平台身份 | `(provider, provider_uid)` 唯一，一个 user 可挂多个身份 |
| `refresh_token` | 登录态 | 存 SHA-256 哈希，一次性使用，可按设备吊销 |
| `asset` | 媒体资产 | 只存对象键，不存 URL；默认 `visibility = private` |
| `video_variant` | 视频播放变体 | 记录 HLS 清单、ts 对象键和状态；播放 URL 按请求动态签名 |
| `cat` | 猫咪档案 | 每用户最多一只 `is_default`（部分唯一索引） |
| `cat_persona` | 人格底座 | 与 cat 一对一 |
| `generation_job` | 生成任务 | `status` 状态机 + `scheduled_at` 支持退避重试 |
| `work` | 作品 | `saved_at` 为空表示还在「最近生成」 |
| `user_quota` | 每日额度 | `quota_date` 做按天重置 |
| `credit_ledger` | 额度流水 | 每次扣减/退还都留痕，便于对账 |

设计上有两条硬约束值得注意：

1. **媒体只存对象键**。数据库里任何一个 `*_url` 字段都会变成过期死链，所以所有图片地址都是请求时现签。
2. **作品与任务分离**。任务可以失败重试，作品只在成功后产生；用户看到的是作品，运维看的是任务。

## 六、多端账号合并规则

这是整套设计里最容易出错、也最需要测试的部分。

```
登录请求 (provider, uid, phone?)
  │
  ├─ 1. user_identity 里有这个 (provider, uid)？
  │      → 用它所属的 user
  │
  ├─ 2. 带了手机号，且该手机号已属于某个 user？
  │      → 把新身份挂到那个 user（跨端合并）
  │
  ├─ 3. unionid 能匹配到已有身份？（同主体微信 / 抖音开放平台）
  │      → 合并
  │
  └─ 4. 都没有 → 新建 user
```

**手机号是唯一的跨端合并键**。抖音小程序拿不到微信的 unionid，所以「用户在微信端建的猫，在抖音端登录后还能看到」这件事，只可能通过手机号绑定实现。

对应地，`scripts/identity-test.mjs` 就是这条契约的回归测试。改动任何账号相关代码后必须重跑。

已知限制：
- 手机号被两个账号分别占用时（账号分叉），接口返回 `CONFLICT`，需要人工合并。这是有意为之——自动合并可能把别人的数据并进来。
- 抖音未绑定开放平台主体时没有 unionid，只能靠手机号。

## 七、生成任务与成本控制

### 为什么必须异步

图片生成 10~30 秒，小程序 `wx.request` 默认超时 60 秒且弱网下不可靠。同步等待会直接表现为「点了没反应」。

```
客户端                      服务端                     Worker
  │  POST /generations        │                          │
  │─────────────────────────▶│ 扣额度 + 插任务(queued)    │
  │◀── { jobId } ────────────│                          │
  │                          │        认领(SKIP LOCKED) │
  │  GET /generations/:id    │◀─────────────────────────│
  │─────────────────────────▶│                          │ 调方舟
  │◀── { status, result } ───│                          │ 转存 COS
  │                          │◀──── 更新为 succeeded ───│
```

### 成本控制的三道闸

1. **每日免费次数**：`user_quota` 用一条 UPSERT 原子扣减，`WHERE` 条件保证并发下不超发。
2. **失败退还**：`refundQuota` 在任务最终失败时退回次数，避免上游抖动吃掉用户额度。
3. **单任务单图**：Adapter 里写死 `sequential_image_generation: 'disabled'`，一次任务只出一张，成本可预测。

### 重试与回收

- 失败重试：`attempt < max_attempts` 时按 `3^attempt` 秒退避，最多 30 秒。
- 僵尸回收：worker 崩溃后 `running` 且 `locked_at` 超时的任务会被重置回 `queued`，超过重试上限则置 `failed` 并退还额度。
- 续锁心跳：生成过程中每 `lockTimeoutMs / 3` 更新一次 `locked_at`，防止长任务被误判为僵尸。

## 九、上海轻量服务器部署

假设已购买：Ubuntu 22.04 / 2核2G / 40GB SSD / 3Mbps。

### 9.1 基础环境

```bash
# Node 20
curl -fsSL https://deb.nodesource.com/setup_20.x | sudo -E bash -
sudo apt install -y nodejs nginx postgresql postgresql-contrib ffmpeg
sudo npm i -g pm2

# 服务器时区（影响 quota_date 的「今天」）
sudo timedatectl set-timezone Asia/Shanghai
```

### 9.2 数据库

```bash
sudo -u postgres psql <<'SQL'
CREATE USER yanmiao WITH PASSWORD '换成强密码';
CREATE DATABASE yanmiao OWNER yanmiao;
SQL
```

按 2G 内存调整 `postgresql.conf`：

```conf
listen_addresses = 'localhost'
max_connections = 40
shared_buffers = 128MB
effective_cache_size = 512MB
work_mem = 4MB
maintenance_work_mem = 64MB
random_page_cost = 1.1
```

`shared_buffers` 默认 128MB 已够用，**不要**调到 1GB 以上——那会让 Node 进程在图片处理时被 OOM。

### 9.3 部署代码

```bash
sudo mkdir -p /www/yanmiao /var/log/yanmiao
sudo chown -R $USER:$USER /www/yanmiao /var/log/yanmiao
# 用 git clone 或 rsync 把项目放到 /www/yanmiao
cd /www/yanmiao/server
npm ci --omit=dev
cp .env.example .env && vim .env      # 见下方清单
npm run migrate && npm run seed
pm2 start ../../deploy/ecosystem.config.cjs
pm2 save && pm2 startup
```

生产 `.env` 必须确认的项目：

```
NODE_ENV=production
HOST=127.0.0.1
PUBLIC_BASE_URL=https://api.你的域名
JWT_SECRET=<48 字节随机串>
DATABASE_URL=postgres://yanmiao:密码@127.0.0.1:5432/yanmiao
WX_MP_APPID / WX_MP_SECRET
DY_MP_APPID / DY_MP_SECRET
COS_SECRET_ID / COS_SECRET_KEY / COS_BUCKET / COS_REGION
AI_PROVIDER=ark
ARK_API_KEY=
DAILY_FREE_LIMIT=3
```

生成随机密钥：

```bash
node -e "console.log(require('crypto').randomBytes(48).toString('base64url'))"
```

`NODE_ENV=production` 时 `config.js` 会做硬校验，缺关键项直接启动失败，不会带着半套配置上线。

### 9.4 Nginx

```bash
sudo cp deploy/nginx.conf /etc/nginx/conf.d/yanmiao.conf
# 修改域名与证书路径后
sudo nginx -t && sudo systemctl reload nginx
```

证书用腾讯云免费 DV 证书，下载 Nginx 版本后放到 `/etc/nginx/ssl/`。

### 9.5 COS 配置

1. 创建存储桶，**访问权限选「私有读写」**。
2. 地域与服务器同区（上海），走内网更省流量。
3. 创建子账号，只授予该桶的 `PutObject / GetObject / HeadObject / DeleteObject`，密钥写进 `.env`。
4. 先执行 `npm run sync:assets` 把 `server/public/assets/` 上传到 `STATIC_ASSETS_PREFIX`（默认 `static/`），再把 `COS_CDN_DOMAIN` 填成 CDN 加速域名并设置 `STATIC_ASSETS_FROM_COS=true`。
   - 该脚本上传时会把对象 ACL 显式设为 `public-read`（可用 `STATIC_ASSETS_ACL` 覆盖）。**这是 CDN 能回源到私有桶的前提**：桶本身保持私有读写，但 `static/` 前缀对象允许匿名读；匿名列举存储桶仍被拒绝。
   - 用户媒体在 `u/` 前缀下存储。`COS_CDN_PUBLIC_MEDIA` 默认 `false`；置为 `true` 后，所有已就绪用户媒体统一返回 CDN 地址，前提是 CDN 侧已完成「私有桶回源」服务授权，否则私有对象会返回 403。访问控制由 CDN 和业务侧保护方案负责。
   - 校验方式：`curl -I https://<CDN域名>/static/brand-logo.png` 应返回 200；`curl -I https://<CDN域名>/u/` 应返回 403。

### 9.6 小程序后台配置

| 平台 | 配置项 | 填什么 |
| --- | --- | --- |
| 微信 | request 合法域名 | `https://api.你的域名` |
| 微信 | request 合法域名 | `https://<bucket>.cos.ap-shanghai.myqcloud.com`（直传需要） |
| 微信 | 业务域名 / downloadFile | 按需，用于保存作品到相册 |
| 抖音 | 服务器域名 → request | 同上两条 |

微信的服务器域名**每月只能改 5 次**，一次配全。

### 9.7 安全组与防火墙

轻量服务器控制台「防火墙」放行：`22`、`80`、`443`。**不要放行 3000 和 5432**。

```bash
sudo ufw allow OpenSSH && sudo ufw allow 'Nginx Full' && sudo ufw enable
```

首次登录后立刻改 root 密码并改用密钥登录。

## 十、上线检查清单

- [ ] `curl https://api.你的域名/healthz` 返回 `{"ok":true}`
- [ ] `pm2 list` 两个进程都是 `online`，重启次数不增长
- [ ] `pm2 logs yanmiao-worker --lines 50` 没有报错循环
- [ ] 真机走一遍：登录 → 建档 → 拍照 → 生成 → 保存
- [ ] 生成失败时额度确实退还（`credit_ledger` 里有 `generation_refund`）
- [ ] 断开网络再操作，客户端有明确错误提示而不是白屏
- [ ] COS 桶权限确认是私有，直接访问对象键应当 403
- [ ] 数据库定时备份已配置（见下）

备份：

```bash
# /etc/cron.d/yanmiao-backup
0 3 * * * postgres pg_dump yanmiao | gzip > /var/backups/yanmiao-$(date +\%F).sql.gz
```

备份文件同步到 COS 并设置 30 天生命周期，不要只留在本地磁盘。
